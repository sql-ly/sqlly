# 2026-11-08

## Scrolling the results grid uses less CPU

A continuous scroll through a result set costs about a quarter less CPU than before, measured back to back against the previous build on a 40,000-row result with a 2,500-character text column on a 120 Hz display (roughly 36% of a core down to 27%). Profiling showed the time split between the grid painter and re-laying-out the rest of the window on every frame. In the grid, long cell values are cut to what can fit the column before they are shaped, each cell's shaped text is kept across frames instead of being rebuilt, and moving the pointer over an unchanged cell no longer repaints. In the workbench, the explorer sidebar, the editor, the in-window menu bar, the tab strip with its command bar, and the status bar are drawn from the previous frame while a scroll only changes the grid (the chrome still refreshes at once on any app change and never lags more than a fifth of a second behind anything else); keyboard-shortcut hints are resolved once instead of per frame, footer selection stats are computed when the selection changes rather than every frame, and masking rules are no longer re-read from disk per frame while unset.

## Optional 60 per second cap on scrolling repaints

A new Settings ▸ Results ▸ Performance ▸ Scrolling checkbox, "Limit scrolling repaints to 60 per second", paces the results grid's repaints while you scroll. On 120 Hz displays it takes another fifth or so off the CPU a scroll costs (about 27% of a core down to 22% in the same measurement) at a slight loss of smoothness; scrolling always lands on the latest position, and the setting has no effect on 60 Hz displays. Off by default.
