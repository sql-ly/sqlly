# 2026-11-23

## Format SQL never re-cases your own names

Formatting no longer changes the case of anything you named. Tables, columns, aliases, user-defined functions (`dbo.fnOrderTotal(…)` or a bare `calcTax(…)`), procedures and user-defined types keep exactly the spelling you wrote. Before, a schema-qualified or unrecognised function call took the function casing (`dbo.fn(x)` became `dbo.FN(x)`), a column defined as `Text nvarchar(10)` or `Date date` had its name upper-cased like a type, a user type such as `MyStatusType` or `dbo.Money2` was upper-cased, and a column called `Type` (or `Key`, `Index`, `View` on PostgreSQL) was upper-cased like a keyword.

Function casing now applies only to built-in functions: each dialect's own functions from the IntelliSense catalog, plus common BigQuery, Snowflake and Redshift functions and grammar written like a call (`ON CONFLICT (`, `ROLLUP(`, `IDENTITY(1, 1)`). With Auto Detect it recognises any supported dialect's built-ins. The Functions setting in Settings ▸ Editor ▸ Formatting is now labelled *Built-in function case*. Built-in data types also follow the data-type casing in `CAST(x AS decimal(10, 2))` and in sized declarations like `DECLARE @n nvarchar(50)`.

The *Identifier case* setting is gone, since names are always left as written. An existing profile that set it still loads; the value is ignored.

## Notebook cells scroll to where you can work on them

Moving to a notebook cell now puts it where it is usable. Selecting a cell with J/K or the arrow keys, jumping to one from the outline, a search match, a history entry or an AI finding, adding, pasting, splitting or moving cells, undoing, Shift+Enter, and pressing Enter to edit all bring the whole cell into view with the smallest scroll that does it. A cell that is already fully visible does not move.

Three cases that went wrong before are fixed. A cell taller than the window used to be shown from its bottom edge, hiding its heading and SQL; it now starts at the top of the window. A new cell added below the last visible one stayed hidden under the edge of the window; it is now shown in full. Pressing Enter to edit a cell that was scrolled partly out of view left it there; it now scrolls to the editor.

If you have scrolled down inside a long cell to read its result, selecting that cell again leaves the page where it is, and only editing it returns to the top. Clicking a cell with the mouse never scrolls, and scrolling by hand always wins over an automatic scroll that is still settling.

## Plans from other tools open in more shapes

Open Plan and Paste Plan from Clipboard now read the output each engine actually prints, not only the one format SQLLY captures itself. PostgreSQL plans open as text (including psql and pgAdmin decoration, BUFFERS, WAL, Settings and JIT sections), JSON, YAML or XML. SQL Server plans open from `.sqlplan` files, plan XML copied out of a grid or Query Store, SHOWPLAN_TEXT, SHOWPLAN_ALL and STATISTICS PROFILE output, with STATISTICS IO and TIME messages attached to the statement. MySQL and MariaDB plans open as the classic table, `\G` output, tab-separated rows, TREE, EXPLAIN ANALYZE and both JSON versions. Oracle DBMS_XPLAN (including ALLSTATS LAST) and AUTOTRACE, SQLite EXPLAIN QUERY PLAN, DuckDB and ClickHouse text and JSON, and CockroachDB EXPLAIN open too.

The engine and format are recognized from the text, so shell prompts, Markdown code fences, line numbers, log prefixes and a plan pasted as a quoted JSON string no longer get in the way. A file with several statements opens all of them. When something cannot be read, the message names what it looks like (for example SQLite bytecode, or a truncated XML file) and what to run to get a plan that can.

## Plan findings name the cause and the statement that fixes it

The findings in the plan pane were rewritten from a short list of generic warnings into a diagnosis of the plan in front of you. Each one says what happened using the plan's own table, columns and numbers ("reads all 600K rows of orders and keeps 5,409"), why that costs time, and what to do next, with a statement in your engine's SQL where one applies: CREATE INDEX with the right key order and included columns, an expression index, ANALYZE or UPDATE STATISTICS, a work_mem setting sized from the spill, OPTION (RECOMPILE), a rewritten date range, and so on. A finding that suggests an index also says what the index costs on writes, and nothing is suggested that the plan does not give evidence for.

The checks now cover SQL Server, PostgreSQL, MySQL, MariaDB, Oracle, SQLite, DuckDB and ClickHouse: scans and filters that discard most rows, functions and type conversions on filtered columns, stale statistics and row estimates that are far off, parameter sniffing and unknown variable values, sorts and hash joins that spill to disk, oversized or delayed memory grants, per-row lookups, nested loops over too many rows, hash joins built on the larger input, joins that multiply rows, subqueries run once per row, CTEs filtered after being materialized, partitions that were not pruned, slow scalar functions, table variables, plans forced to run serially, skewed or missing parallel workers, JIT and planning overhead. Each check has thresholds on both the absolute row counts and the share of the statement's time or cost, so a 20-row lookup or a scan of a small table is no longer reported.

Findings are ordered by how much time fixing them would save, and each shows that share. When two findings need the same index it is written once, a wider index absorbs a narrower one on the same table, and the SQL Server optimizer's own missing-index request replaces the generic scan warning for the same operator. A finding rated critical is only shown that way when the statement actually ran long.

When table definitions are supplied with a plan, the advice uses them: it does not suggest an index that already exists, extends an existing index instead of adding a near-duplicate, points out an index the plan ignored and the likely reason (a value of a different type, an estimate that made the scan look cheaper), and flags joins on foreign keys with no index, joins on columns whose types or collations differ, NOT IN over a nullable column, large tables with no clustered index or primary key, very wide indexes, and a plan that refers to tables or indexes the definitions do not have.

## The plan pane reads like a diagnosis, with a diagram, operator table and time chart

The execution plan pane was rebuilt. It now opens on a Summary that says in sentences what the query did, step by step, names the step that cost the most, and lists the findings in the order worth fixing, each with its evidence, how sure the diagnosis is, alternative fixes and links to articles on sqlly.app. Clicking a step or a finding selects that operator in every other view.

The Diagram draws each operator as a card with its table, rows and share of the time. Cards can be coloured by time, cost, rows, estimate error or I/O with a legend, connectors are thicker where more rows flow, the most expensive path is marked, and the heaviest operators carry a text badge so colour is never the only signal. You can flip the diagram between top-down and left-to-right, zoom, pan, fit it to the pane, fold branches, search for an operator or table, walk the tree with the arrow keys, and jump around a large plan with the minimap. The old tree view is replaced by a sortable Operators table, and a Time view shows a flame chart with totals by operator, operator family and table.

Selecting an operator anywhere opens a details panel that explains what the operator does, shows its numbers and predicates, and resolves a table alias to the real table name when the query text or the connection's known tables allow it. When the plan was captured on a connection whose tables the app already knows, findings use your column types and keys and say so. Estimated plans and plans without timings say what is missing instead of showing empty numbers.

Comparing two captures now explains the difference in sentences, each marked better, worse or neutral, and a plan file that cannot be read shows what it looks like and what to run instead inside the pane. Notebook Plan cells use the same summary, findings and comparison in a compact form.

Plans with more than 500 operators are analyzed in the background. The pane says so while it works (and says so plainly if the analysis fails), and the status bar and the Plan tab's finding count are filled in when it finishes instead of showing the previous plan's count. The "Bottleneck" badge appears only on a step the summary calls the bottleneck; when no single step dominates, the slowest step is named without it. A diagram card carries a warning mark only for a finding listed beside it, connector row counts use the same figure and rounding as the card they come from, and card titles that do not fit end in an ellipsis and show in full on hover. Plan numbers use the interface language's separators (1.760 Zeilen in German), long finding and summary text wraps instead of running off the pane, and in languages other than English the Learn more links name the kind of page and its address instead of an English title.

## Plan times, estimates and comparisons are more accurate

SQL Server plans that mix batch-mode and row-mode operators now add up to the statement's elapsed time; before, batch-mode operators could be charged with time spent below them. On the inner side of a nested loop the estimate is compared with the rows of one execution, and one execution spread over several threads is no longer counted as several loops. In PostgreSQL plans an InitPlan is charged once. Oracle DBMS_XPLAN text and DuckDB text profiles print step times in hundredths of a second. When a statement is too short for those steps to tell operators apart, the plan now says so and ranks steps by cost or rows instead of showing per-step times that are rounding noise.

CockroachDB, Trino and Spark plans are recognized as their own engines, with their own operator explanations and findings, and DuckDB and ClickHouse plans get engine-specific findings.

A filter on a window function's result, such as `WHERE rn <= 10` over ROW_NUMBER, is no longer reported as a row estimate that is far off. A SQL Server bitmap filter pushed down from a join is described as that, instead of showing `PROBE(Opt_Bitmap…)` as if it were the query's filter. Large factors are written out ("10,000×" rather than "10.0K×").

Comparing an estimated plan with an executed one now says which is which and that only costs, row estimates and plan shape are compared. A table the new plan reaches through an index (a PostgreSQL Bitmap Heap Scan, an Oracle TABLE ACCESS BY INDEX ROWID) is reported as a change of access path, not as a table the plan no longer reads.
