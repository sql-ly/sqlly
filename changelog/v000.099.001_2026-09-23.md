# 2026-09-23

## MySQL results are readable again: counts, sums and dates stopped arriving as hex

On MySQL, anything that was not a plain text or number column came back as a dump of hex digits instead of its value. `SELECT COUNT(*)` showed `0x32` where it meant 2; sums, averages and any calculation did the same; and every DATE, TIME, DATETIME and TIMESTAMP column read that way too, so an ordinary `SELECT *` on a table with a timestamp was unreadable. MySQL marks everything that is not a character column as "binary", including dates and computed values, and SQLLY was taking that mark at its word. It now asks what the column actually is, so values read as values while real binary columns — BLOB, VARBINARY, images — still arrive as binary and can be saved or viewed as hex on purpose.

## MySQL follows your USE statement instead of quietly pointing somewhere else

Running `USE other_database` on a MySQL connection changed which database your statements actually ran against, but nothing in SQLLY said so: the status bar, the explorer and the tab's target kept naming the database you originally connected to, while every later query ran somewhere else. Worse, the connection went back into the reuse pool labelled with the old database, so a query you ran afterwards could land on the wrong one without any indication. SQL Server has always confirmed the change and told you; MySQL now does the same, updating what the window shows and noting the switch in Messages. If the confirmation itself cannot be made, SQLLY says so and reconnects rather than carrying on with a connection whose database it can no longer vouch for.
