# 2026-11-19

## SQL notebooks, rebuilt

Notebooks are now a full part of SQLLY instead of a command-palette extra. File has New Notebook, Open Notebook… and Save Notebook, the Query menu has Run Notebook Cell, Run All Notebook Cells and Stop Notebook Run, and right-clicking a query tab offers Open as Notebook (as one cell, or one cell per statement); Convert to SQL Script turns a notebook back into a single script. A notebook has a top bar with its title, save state, connection, run mode, Run All, Stop and a Run menu; a left rail with the outline, parameters, named cells, which cells feed which, local data, run history, bookmarks and search; a right inspector for the selected cell's connection, safety settings, dependencies, state and last run; and an activity panel with the run queue, timings and errors. Every panel can be hidden and resized, Zen mode hides them all, and Dense cells fit more on screen. Notebooks save as `.sqllynb` files with stable cell ids, predictable formatting and no query results, so they diff cleanly in Git, and settings written by a newer SQLLY are kept when you save. Older `.sqlnb.json` notebooks and Jupyter `.ipynb` files still open: cells in an older notebook that change data stay runnable, new cells start read-only, an older file is only replaced when you choose Save, and Jupyter files keep other tools' metadata (such as papermill parameters and Azure Data Studio cell ids) and raw cells.

## Notebook cells that know what they depend on

Give a cell a name and use it as a table in another cell with `{{name}}`, even in cells that start with `SET NOCOUNT ON`, `DECLARE`, `SET search_path` or `GO` batches. A referenced query on the same connection is folded into the query that uses it, references inside strings and comments are ignored, circular references are reported with the full chain and a suggested fix, and renaming a cell updates every cell and formula that uses it. Each result is tied to its SQL, parameters, connection, sign-in and safety settings and the cells it reads, so changing one parameter marks only the cells that use it as out of date and an old result is never shown as current. Run one cell, a cell with its out-of-date inputs, everything, only what is stale, everything downstream, above or below, or a selection, or check the plan without running. Cells that don't depend on each other run side by side (two per connection by default), cells that share a session run one after another, and a cell that fails or can't start stops only the cells that read from it. Stop, closing the tab and disconnecting cancel every query the notebook has running, relay connections included, and a query that finishes after Stop never replaces the canceled result.

## Each notebook cell picks its connection, and runs read-only by default

A SQL cell can run on any saved connection, with its environment shown beside it, while the others keep the notebook's connection; "Use the tab's connection" moves the notebook's cells to the tab's connection in one step. New cells run in the database's read-only mode. A cell that changes data runs only after you choose Allow writes and confirm it against the named connection, and the usual change review then says which connection and environment the change goes to. Plan cells always run read-only and refuse a query with more than one statement, and local cells and Materialize Locally never run a data-changing cell again: they copy the result already on screen.

## Shared notebooks never run until you trust them

Opening a notebook never runs anything, and SQLLY checks every file it opens (files, recent files, restored sessions, recovery copies and the browser) before showing it: oversized or deeply nested files, connections that contain passwords and attachments that point outside the notebook's folder are refused with the reason, and things worth a look, such as web images or a notebook asking to run itself, show in a banner and the activity panel. Trust comes from this computer's own records, not from the file. A notebook you create stays trusted as you edit and save it, while one from anywhere else, or one whose queries or connections changed outside SQLLY (after a git pull or in a synced folder), opens untrusted and shows no saved results. Trust notebook opens a dialog listing the notebook's connections and the connection each maps to on your computer: untick any it shouldn't use, choose full or read-only trust, and allow data-changing cells only if it needs them. A connection you remap afterwards waits for your OK again. A copy of a notebook file gets its own identity the first time you save it, so the two never share trust, run history or local data.

## Every notebook action is checked and logged

Running a cell, timing a query across parameter values, exporting, saving results locally, sending context to a cloud AI model, scheduling and presenting a notebook are each checked against its trust and allowed connections at the moment they start. Data-changing cells need your go-ahead, production connections are labelled, a diff that compares against another connection needs that connection allowed and present, and notebooks with data-changing cells can't be presented as apps. Every run, refusal, trust decision and export goes into a local notebook audit log with timings, row counts and what redaction removed, but never the SQL text or the data.

## Typed notebook parameters

Parameters have types (text, numbers, switches, dates, date-times, date ranges, lists, lookups, sliders, allow-listed table names and secrets) and show the matching input in a Parameter cell or the Parameters tab of the left rail, with mistakes explained under the input. A parameter editor sets the name, label, type, default (dates also accept phrases such as "last week"), allowed values, validation, sensitivity, whether each person keeps their own value, and whether changes wait for Apply; renaming a parameter updates every cell that uses it. Values are written into each database's SQL as safe literals, table names come only from the allowed list, and secrets refuse to be written into query text. The Presets menu offers moving date presets such as Last 7 days, Previous month and Current quarter, plus named presets, and you can save every current value as a set for everyone or just for yourself; personal values and sets stay on your computer and out of the file. Dropdowns, multiple-choice lists and lookups can take their choices from a small read-only query (up to 1,000 rows, cached, with a reload button) and refresh when the parameter they depend on changes.

## Apply before notebooks query the database again

With Re-run on change switched on, a parameter change re-runs local cells straight away while cells that query a database wait in an Apply bar listing them with their connection and environment, so a burst of edits never floods a server. A parameter can also wait for Apply before any cell sees its new value.

## Sensitive parameter values stay private

Sensitive values are masked on screen, shown as dots in text cells, never saved in the notebook or your personal file, and kept out of query history, run records, saved sets, exports and the audit log, including through local cells and formulas that read them.

## Local data with DuckDB in every notebook

Each notebook can keep results and data files in its own DuckDB database on your computer. A SQL cell set to Local (this notebook) can use other cells as tables with `{{name}}` even when they come from different connections, such as SQL Server orders joined with Postgres targets: SQLLY copies those results in first, asking the first time for each connection and once per cell unless you let the notebook do it, and the cell shows which connection and environment each input came from, when it was read, how many rows it has and whether a limit cut it short. Materialize Locally As… keeps a copy of any result under a name you pick, offering to run a reading query again to copy every row when only part is on screen. The Local data tab lists every table with its size and origin, refreshes, drops or exports it to Parquet or CSV, clears everything, shows how much of the space limit is used, and has an Encrypt local data switch that encrypts the database with a key kept in your system keychain (with tables present, it asks you to clear local data first). Local SQL can only read the notebook's own tables: it can't open other files, download extensions or change settings, row and size limits stop runaway imports, and older notebooks' local data is cleaned up when the total grows past its limit. Values of mixed types show as text instead of failing.

## Attach data files and pictures to a notebook

An attachment cell imports a CSV, Parquet, JSON, NDJSON or SQLite file into a local table with a preview, the row count and the detected column types, and notices when the file changes. Files next to the notebook are remembered by relative path, files from elsewhere are read again only after you pick them on this computer, and paths that lead out of the notebook's folder through a link are refused. PNG and JPEG attachments are checked before they are shown, and a Markdown cell can show one with `![caption](attachment:name)` in trusted notebooks. Markdown cells never load images from the web or other files; those show as a small placeholder.

## Charts in notebooks

Add a Chart cell under a query and pick one of three suggested charts or build your own from 17 chart kinds (bar, line, area, scatter, bubble, histogram, pie, donut, heatmap, calendar heatmap, waterfall, funnel, treemap, box plot, cohort retention, correlation matrix and sparkline) with date grouping, top N with an Other bucket, sorting, missing-value handling, value formats and currencies, reference lines, annotations and an expected-range band that marks unusual points. Bar, line, area, scatter, histogram, pie and donut charts draw live; the rest draw exactly as they will in exported reports, in colour-blind-safe colours in light and dark themes, and any chart saves as SVG or PNG. "Other" is computed from the rows it groups, so its average, minimum, maximum or median is right, and a chart with more categories than it can draw groups the rest under "Other" and says so.

## Formatted tables, pivots and KPI scorecards

Table cells show a result with its formats, conditional colours, computed and frozen columns, search and column statistics, saved with the notebook. Pivot cells keep their layout and let you double-click a value to see the rows behind it. KPI cells put up to eight tiles in a row, each comparing a total, count or value with the previous period, another cell's result or a target, with direction-aware good, warning and critical status and a sparkline.

## Report-style notebooks with embedded outputs

Any notebook cell can show just its output: a query shows its result grid with no editor, toolbar, result tabs or side panels, a pivot shows the pivot table, a chart shows the chart, sized to fit and sitting flush with the cells around it, so a notebook reads like a report. Turn it on per cell from the cell menu or with E in command mode, or for the whole notebook with Embed All Outputs in the More menu or the command palette. Hover an output to show it in full again, run it, open its menu or drag its bottom edge to resize it. A cell that hasn't run shows a Run button, failures stay visible, and out-of-date, partial or running results keep a small mark. An embedded pivot or chart can show or hide its settings beside it, so a report can keep the pivot's fields or the chart's options at hand or show only the result. Embedding never runs anything and exports ignore it.

## Lock a result grid to rows, pivot or chart

Lock view in a query or table cell's menu holds its result grid on its rows, pivot or chart, so readers of a shared notebook see the view the author chose. Double-clicking a pivot value or clicking a chart bar in a locked grid lists the rows behind it underneath. Only the active result of a multi-statement cell is embedded or locked.

## Formula cells that keep every digit

A formula cell computes one value from earlier results and parameters, such as an average order value, with arithmetic, comparisons, if, coalesce, rounding, date differences and column totals, and shows it large. Whole numbers and decimals are held exactly, so a 19-digit ID or a decimal(38,2) total keeps every digit, and a value that had to fall back to floating point says it's approximate. Write `{{name}}` to show it in Markdown, as plain text, or to use it in a later SQL cell, where it's written into the query safely. Formulas can't read files or the network.

## No-code transforms

Transform cells filter, choose and rename columns, add computed columns, group, join another result (or the same one), sort, limit, pivot and unpivot, step by step with undo. They show the SQL they generate and run it on the rows already downloaded, in the notebook's local data, without sending anything to the database. Filters compare what you typed against the column's own type, so 007 matches a text zip code and long IDs keep every digit; "contains" and "starts with" ignore case, "is not" leaves empty values out unless you tick Keep empty values, and steps after a pivot offer the pivoted columns.

## Click a chart to filter linked cells

Set a table, chart, pivot or KPI cell to follow a chart, then click a bar, point, slice, funnel stage, treemap tile or waterfall step: the following cells show only that category, with a filter chip to clear it. It works on bar, line, area, scatter, pie, donut, funnel, treemap and waterfall charts, and on bar, line, area, pie and donut charts with reference lines, annotations, stacking or anomaly bands; histograms, heatmaps, box plots, bubble charts and the other grid-style charts can't be clicked yet. Filtering uses the rows already downloaded and never runs a query.

## Charts and KPIs say when they saw only part of the data

Every visual cell can show the SQL behind it, the cells and table columns it depends on and where and when its data was fetched, and open that SQL in a query tab. A chart, KPI, formula or check computed from a result that was cut short, sampled, stopped early or only partly read back from disk says so, and a SQL cell that uses such a value is marked "Computed from partial data" in the cells that read it and in exports. Sparklines carry a small warning mark.

## Profile any notebook result

A Profile cell shows a card for every column of a result: type and likely meaning (dates, emails, IDs, money and more), missing and distinct values, range, average and spread, percentiles, a histogram, the most frequent values, outliers and whether the column can serve as a key, with a summary grid you can sort. Large results are profiled within a fixed memory budget and estimated figures are marked. When the input is a table in the notebook's local data that holds more rows than the result shows, the counts, ranges, averages and quartiles cover the whole table, and each card says which figures cover the whole table and which only the first rows.

## Tests in notebooks, with the evidence

An Assertion cell checks row counts, uniqueness, missing values, ranges, allowed values, text patterns, matching keys between two results, drift from the previous run or a pinned snapshot, freshness (in a time zone you choose, warning on rows dated in the future), query duration and KPI thresholds. Each check shows pass, warning, fail, error or inconclusive with the numbers it saw and up to 20 failing rows, and a result that was cut short or sampled makes a check inconclusive rather than a false alarm unless you allow partial data. The top bar counts failing tests, shows the last recorded run's results as soon as the notebook opens, and Run All reports them.

## Compare two results or two runs

A Diff cell compares two results, the same cell now and in an earlier run or snapshot, or the same query on another of the notebook's allowed connections, pairing rows by key columns with tolerances for rounding, letter case and spacing. It lists added, removed and changed rows in separate grids, reports column changes, and compares large IDs and wide decimals exactly.

## Query plans, plan comparison and parameter sweeps

A Plan cell shows the estimated plan of another cell's query, or its actual plan once you confirm the query may run, with findings and the operator tree, and Explain with AI adds an AI cell on its most expensive steps. Compare it with another version of the query or the previous run to see which operators got costlier or cheaper, read session counters on SQL Server and MySQL, and time the query across a list of parameter values with averages and spread. Every figure says which database and measurement it came from, and sweeps refuse data-changing cells and ask before timing a query on a production connection.

## Explore the rows related to one record

An Entity Detail cell takes a row from a result, the row selected in a table cell, or a value such as a customer ID, and shows the related rows from the foreign keys you approve, each in its own grid. Lookups are read-only and limited, you can step through the source rows, and any related set opens as a new detail cell.

## Run history, snapshots and run comparison

Every notebook run, in the app or from the command line, is recorded with its time, parameters (sensitive values never written), which cells ran or failed, test results and KPI values, and the History tab lists them. Pin a cell's result as a named snapshot kept encrypted on this computer, open a past run's results, and compare two runs to see, cell by cell, whether its SQL, parameters, connection, an input cell or the data itself changed, with row-count and test differences.

## Notebook dashboards

Add a Dashboard cell, or press Dashboard in the top bar, and place any result, chart, KPI or note on a 12-column grid: resize tiles by dragging their edges, drag them to reorder, and split the dashboard into sections and tabs. Tiles can have titles and notes, appear only when a filter has a value or a check passes, and drill through to another tab with a filter set to the value you pick. The filter bar uses the same typed inputs as the Parameters panel, and filters that wait for Apply show as waiting in both places. The dashboard reflows on narrow windows and is saved in the notebook file.

## View or present a dashboard without the SQL

View shows only the dashboard, its filter bar, drill-throughs and Refresh, which says how many queries it will run and on which connections, production included, before anything runs. Present shows it full screen one section per slide or all at once, moving with the arrow keys, Space, Page Up/Down, Home and End and leaving with Esc, and a dashboard can force the light or dark theme (your own theme comes back however the presentation ends) and carry your logo. Notebooks with data-changing cells can't be viewed or presented this way, and SQLLY names the cells that need to be made read-only.

## Export notebooks as reports

Export… opens one dialog for a self-contained web page, a paged PDF with bookmarks, page numbers and repeated table headers, an Excel workbook with a summary sheet and one sheet per table, Markdown with chart images, CSV, SVG and PNG charts, and clean notebook and Jupyter copies. Choose a layout (executive, technical incident, audit, financial or operational), the whole notebook, a dashboard or selected cells, where the SQL and data sources go, whether row data leaves your computer, and current results or a saved run from the app or the command line. Numbers, dates, titles and chart series match across formats, large and very precise numbers keep their digits, dashboards keep their side-by-side layout in web pages and PDFs, and each section can start a new PDF page. Report text follows the app's language.

## Exports that say what they left out

Before writing, the Export dialog lists the files, what the chosen format can't show (interactive charts, side-by-side dashboard columns, characters the PDF font lacks, categories grouped under "Other", times converted to UTC) and what will be removed. Charts drawn from incomplete data carry their badge inside the picture in every format, CSV notes tables that hold only part of their result, and KPI notes and inconclusive checks keep their status. Exports leave out sensitive parameters, sensitive columns and anything that looks like a password, key or token, ask first when sensitive data was found, and a structure-only export drops all rows, totals and the numbers checks and KPIs quote. Scripts and unsafe links never make it into a report, and spreadsheet cells that look like formulas stay plain text.

## AI analysis cells in notebooks

Add an AI cell, ask a question and pick a mode: Assist explains errors and suggests fixes or charts, Plan writes an investigation plan you approve before anything runs, Build turns it into proposed cells, Investigate runs a few read-only queries and reports findings, Review checks your SQL, and Explain changes says what changed since the AI last looked, or between two runs from the notebook's history. A budget meter shows queries, rows, query time, tokens and turns against their limits, and Stop ends a run. Cloud AI profiles take optional prices per 1,000 input and output tokens in Settings; with a price set, the meter shows the estimated cost and a cost cap stops the run. A failed SQL cell offers Explain with AI, and Explain Last Error on a notebook tab does the same.

## AI findings that show their evidence

Every finding is labelled as an observed fact, a derived metric, a hypothesis or a recommendation, links to the cell, run or query it rests on, and is marked Unverified when nothing was run, the evidence wasn't read, the quoted number isn't in it, or it covers only sampled or partial data. Findings that contradict each other stay side by side, and the labels carry into exported reports. Before the model looks, Review checks each query for totals inflated by joins that repeat rows, counts over joins, distinct sums, reused or out-of-date results, sampled data, cells that skip the notebook's filters, server-clock time zones and data-changing cells, and confirms repeated join keys from the cell's own results.

## AI proposals you approve one by one

The AI never edits a notebook directly. It proposes new cells (including plan and entity detail cells), edits, settings changes and runs, each with Accept and Reject, and Apply accepted adds them as cells marked as created by AI that Undo AI changes removes together. Anything that would change data, touch a data-changing cell, move a cell to local data or another connection, or doesn't fit the cell type is refused and labelled. With a local model the AI cell runs right away; before a cloud model is used, the cell shows exactly what will be sent and what never is (credentials, passwords and tokens, sensitive parameters and sensitive-looking columns), and nothing leaves your computer until you choose Share and run. The agent reads only through the notebook's trusted connections within its budget, text in your data can't give it new permissions, and a local log records each run's model, tools, approvals and result fingerprints without your prompts or data.

## Run and check notebooks from the command line

`sqlly-cli notebook run` runs a notebook against your saved connections without opening the app: pick parameters, map each connection, run every cell, a selection or only what is out of date, and get an exit code your scripts can act on when a cell fails or a check doesn't pass. It runs SQL, local, attachment, test and KPI cells as the app writes them; read-only cells stay read-only, data-changing cells and production connections are refused unless you allow them, the notebook has to be trusted on this computer, and the results it keeps are encrypted like the app's. `sqlly-cli notebook validate` reports circular and broken references, missing connections, unsafe cells, bad parameters and suspicious files in a form CI can read, and `sqlly-cli notebook diff` compares two notebooks cell by cell (added, removed, moved, renamed, SQL as a line diff, settings, parameters and connections) and plugs into `git diff` and `git difftool`. `sqlly-cli notebook runs compare` explains, cell by cell, why a result changed between runs.

## Export runs and dashboards from the command line

`sqlly-cli notebook export` writes any recorded run as HTML, PDF, Excel, Markdown, CSV, SVG or PNG with the same layouts, removes sensitive values, can leave out all data or all SQL, and lists what the format couldn't show. `--dashboard` exports one dashboard with its sections and grid, and `--page-per-section` starts each section on a new PDF page.

## Scheduled notebooks with alerts

`sqlly-cli notebook schedule add` runs a notebook on this computer's own scheduler (launchd, systemd or cron, Task Scheduler) in the time zone you choose, handling daylight saving changes, retrying failures and pausing a job that keeps failing. Alerts go to a desktop notification or a webhook only when something starts or stops going wrong, wait out quiet hours unless critical, and never fire on incomplete data unless you ask; there are no email alerts. Webhook addresses are kept in the system credential store, not the schedule file. Schedules run only while this computer is on, never change data, and stop if the notebook is edited outside SQLLY until you trust it again. On Linux, systemd user timers stop when you log out; the command warns about it, and `--enable-linger` keeps them running.

## Saved notebook results are encrypted and private to your sign-in

A cell's result can be kept for this session only or saved encrypted on this computer with a key in your system keychain, reused while nothing changed, for a set time or until you run the cell again, and cleared when its connection disconnects. Saved results are filed under the connection, database, sign-in and safety settings that fetched them, so another sign-in never sees them, a damaged or altered file is discarded, and they come back as soon as a trusted notebook opens. Results expire, the oldest are cleared when space runs short, and you can clear them for one connection or all at once.

## Row limits that say when a result is cut short

A cell's maximum rows (and download size) stops its query at the limit, even for results large enough to be kept on disk, and says the result is incomplete instead of presenting it as whole; Fetch All runs it once without the limit.

## Select, copy and paste notebook cells

Shift-click, Shift+J and Shift+K, or Cmd+A in command mode select several cells, and a bar above them runs, copies, cuts, duplicates, moves, collapses, converts, merges, bookmarks or deletes all of them at once. Copied cells paste into the same or another notebook with new ids, names that don't clash and references pointing at the pasted copies; other apps get them as a SQL script or as Markdown with the SQL in code blocks, SQL pasted into a notebook becomes one cell per statement, and pasted cells always start read-only.

## Undo and redo any change to a notebook's cells

Inserting, deleting, moving, pasting, renaming, changing settings or connections, find and replace and AI changes are each one step you can undo with Z or Cmd+Z in command mode and redo with Shift+Z or Cmd+Shift+Z, while undo inside a cell's text stays separate.

## Reorder, split and merge notebook cells

Drag a cell or the whole selection by the handle at the left of its header, with a line showing where it will land, or press Option+Up and Option+Down. Cmd+Shift+Minus splits a cell at the cursor and Shift+M merges it with the next one.

## Slash menu, find and replace, and reference completion in notebooks

Type / at the start of a line in a Markdown cell for headings, lists, tables, callouts, a cell reference, a parameter value or a new cell of any kind; the + between cells and I in command mode insert any kind of cell. Cmd+F and Cmd+Shift+H search SQL, Markdown, cell names, the title and chart titles and notes, optionally result values too, and replace everything in one undoable step. Typing {{ lists the cells and parameters you can use, after FROM {{orders}} o typing o. offers that cell's columns, and hovering a reference shows the cell's kind, state and columns.

## Bookmarks, folded sections and pinned results

Bookmark cells with Cmd+F2 in command mode and move between them with F2 and Shift+F2, see them in the Bookmarks tab, fold a Markdown heading to hide its section, and pin a cell's result to a strip that stays above the cells while you scroll.

## Run notebook cells from the keyboard

Cmd+Enter runs the cell you are in, Shift+Enter runs it and moves on, and Option+Enter runs it and opens a new cell below (Ctrl and Alt on Windows and Linux). Esc switches to command mode, where J and K move between cells, A and B insert cells, D twice deletes one, M and Y switch between Markdown and SQL, E embeds the output and Enter starts editing. Every shortcut can be changed in Keyboard Shortcuts, and every notebook command is in the command palette.

## Notebook autosave, recovery and save conflicts

A notebook you haven't saved keeps a recovery copy and comes back after a restart or crash, a saved notebook you quit with unsaved changes reopens offering to restore or discard them, and one whose file was moved comes back as an unsaved notebook. Saved notebooks can save themselves as you edit (off by default). If the file changed on disk, or in another browser tab, Save waits while you choose Reload or Keep mine, and opening a notebook that's already open switches to its tab.

## Notebooks in the browser version

The browser version opens and saves notebooks and Jupyter files from your computer, and keeps a copy of every notebook you open or save in that browser, so unsaved notebooks, recovery copies, trusted notebooks, run history and recent files survive a reload. In Chrome and Edge, Save writes back to the file; other browsers download it with Save As. The Export menu downloads web pages, Excel workbooks, Markdown, CSV, SVG charts, SQLLY notebook copies and Jupyter notebooks with the same removal of secrets and sensitive values; PDF and PNG need the desktop app and say so. Cells that need the desktop app (local data cells, transforms, attachments and export cells) say so when the notebook opens, the cells reading them wait instead of erroring, and run history notes that cell results aren't kept in the browser.

## Notebooks in your language

Every notebook message, including parameter, formula, transform, plan, local data and trust errors, run history rows, option names and the text reports write, appears wholly in the app's language, and messages kept in run history follow you when you switch languages. Server error text stays as the server wrote it.

## Large notebooks stay responsive

Notebooks with hundreds or thousands of cells stay smooth: cells you aren't editing show a lightweight highlighted preview, editors appear when you click into a cell, and SQL areas grow with their content. A keystroke now redraws only what it changed, with the other cells' editors and result grids drawn as they were, and no longer walks the whole notebook to rebuild the outline, search, find, folds, completions or undo history; those catch up once typing pauses, and the check for stale results then re-reads only the cell you changed. To keep long notebooks light, each cell's run, move, collapse, delete and menu buttons now appear on the cell you are on or pointing at; the other cells show their kind, name, state, connection and safety labels without them. In our measurements typing in a 1,000-cell notebook takes about 2 ms of work per keystroke, scrolling about 2 ms per frame, and the pause after typing about 6 ms.

## Estimated plans work on read-only SQL Server connections

On a SQL Server connection set to read-only, the estimated plan failed with "The SET SHOWPLAN statements must be the only statements in the batch": the read-only safety wrap was added around the statement that switches plan capture on. That statement now runs on its own, the query in between is still checked by every read-only rule, and since the server only compiles it while plan capture is on, it is sent without the wrap so the plan shows only your query. Notebook Plan cells, which always run read-only, use the same capture.

## An OpenAI-compatible AI profile without a key is used

Choosing an OpenAI-compatible profile that has no API key (a local or self-hosted endpoint) as the app's AI backend no longer falls back to the local model: a profile saved without a key now reads as having no key instead of failing the keychain lookup.

## Hover cards are no longer cut off by the editor's edge

A hover card in a short editor showed only its first line because it was trimmed to the editor's own area. Hover cards now draw over the whole window, like the editor's menus, and show in full.

## Large execution plans open

An Estimated or Actual plan whose plan document was longer than 8 KiB, which is common for SQL Server queries with a few joins, failed with "XML parse error" (or a JSON error on PostgreSQL, MySQL and DuckDB) because the plan was read like a grid cell and cut to its first 8 KiB. Plans are now read in full in the query tab, in notebook Plan cells and in the plan summary shown before an AI assistant's query runs.
