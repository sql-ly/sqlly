# 2026-10-14

## Export to file works in the browser version

In the browser version of SQLly, exporting results to a file used to do nothing (it only logged that file exports were desktop-only), and Excel exports couldn't be produced at all. Saving an export to a file — from the Export… dialog or by shift-clicking a format in the Export dropdown — now downloads the file through the browser, named like the desktop default (for example `results.csv` or `results.xlsx`).

## Copying grid selections works in the browser version

In the browser version, selecting rows or cells in a results grid and pressing ⌘C (or Ctrl+C) put nothing on the clipboard. The copy shortcut now works there and copies the selection in your default copy format, with ⌘⇧C / Ctrl+Shift+C including headers. On Windows and Linux desktops, Ctrl+C in the grid now also honors the default copy format instead of always copying tab-separated text.

## Closing the browser version closes the tab

In the browser version of SQLly, the red close button in the title bar used to tear the app down and leave a blank page, and Quit did nothing. Both now save your session and ask the browser to close the tab. Browsers only let a page close tabs that a script opened, so when the browser keeps the tab open, SQLly stays running and a notification says to close the tab with ⌘W or Ctrl+W.

## Open in Spreadsheet works in the browser version

In the browser version, Open in Spreadsheet used to be missing from the grid's right-click menu and showed "not available" everywhere else. It now builds the same file the desktop app opens (an Excel workbook, or a CSV Excel reads correctly when Excel export is turned off) and downloads it, from the grid menu, the Export dropdown and the Export… dialog. A browser page can't start Excel itself; a browser set to open that file type automatically (Chrome's "Always open files of this type", Safari's "Open safe files after downloading") opens the download in Excel straight away.

## IntelliSense Improvement: subquery aliases in FROM and JOIN are recognized

A parenthesized subquery used as a table (`FROM ( SELECT … ) t`, with or without `AS` before the alias) was not recognized: typing `t` in the outer WHERE only offered columns of other aliases starting with t, such as `tl.*`, and `t.` offered nothing. The subquery's alias now offers the columns its select list produces — each item's alias, a `Name = expr` target, or the column's own name — ahead of longer aliases that merely share the prefix, in FROM and JOIN positions and for subqueries that start with a CTE (feedback ifb_8e1f).
