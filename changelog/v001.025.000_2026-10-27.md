# 2026-10-27

## Query Builder opens fast on big databases and shows when it is still loading

A customer opening Design Query on a table found the Query Builder slow to fill in, with no sign of whether it was working or frozen. Two things caused it. The table list on the left was rebuilt in full (filtered, sorted, one row per table) on every redraw, including every mouse move while dragging a card and every keystroke, so databases with thousands of tables made the whole dialog sluggish. The list is now computed once and only the visible rows are drawn. Also, the builder kept the table list it had when it opened, so opening it right after connecting or switching databases showed an empty list, and the table picked with Design Query was quietly dropped. The builder now picks up the table list as soon as it arrives, shows a spinner with "Loading tables…" (or "Refreshing table list…" when it is showing a cached list), adds the Design Query table once it shows up, and says so plainly when a database has no tables or nothing matches the filter. The explorer's "Design Query" item on tables and views is now called "Open in Query Builder", so it names the dialog it opens.

## The explorer and IntelliSense catch up after you change the schema

Running CREATE, ALTER, DROP or RENAME in a query tab used to leave the explorer showing the old schema until you refreshed it by hand: a new table didn't appear, and an expanded table kept listing a column you had just added or dropped. Now any run containing one of those statements (anywhere in the batch, including T-SQL's IF … DROP TABLE form) refreshes that server's explorer tree, keeping whatever you had expanded, and reloads IntelliSense, so a new table shows up in place and an expanded table's columns update after ALTER TABLE … ADD, DROP, ALTER or RENAME COLUMN. The refresh also happens when the batch fails or is cancelled part-way, since earlier statements may already have changed the schema. Refreshing the explorer, by hand or after a run, also no longer briefly refills an altered table from the previous IntelliSense snapshot before the fresh one arrives.

Answers [DbGate #1493](https://github.com/dbgate/dbgate/issues/1493) (a table created with a CREATE TABLE query doesn't appear until the app is restarted).

## SQLite explorer and IntelliSense read the connection's own file

On a SQLite connection made in the connection editor, expanding the database's main node showed every folder as empty, and IntelliSense had no tables, because the explorer and IntelliSense asked for the database by its schema name ("main", or a "master" default) and SQLite opened an empty file with that name in the app's working folder instead of your database. A plain schema name like that now always means the connection's own file, so the explorer lists your tables and IntelliSense completes them, and no stray empty files are created. A database field that holds an actual file path still wins, as before.

## Filter a table's columns in the structure editor

Finding one column in a wide table meant scrolling the whole list in Edit Structure. The Columns tab now has a filter box that narrows the list to columns whose name, data type or description contains what you type, ignoring case, so you can find a column by the comment your team wrote on it. Edits made while filtered apply to the columns you see, the change script still covers the whole table, Add column clears the filter so the new row is visible, and clearing the filter brings back the full list with your changes intact.

Answers [Sequel Ace #2271](https://github.com/Sequel-Ace/Sequel-Ace/issues/2271) (Structure filter should match column comments).

## Hide schemas you don't use, per connection

Databases with dozens of schemas can bury the few you work in, and until now SQLly could only hide system schemas, for every connection at once. You can now hide any schema from the explorer for one connection: right-click it and choose Hide Schema (or, in the default layout that lists objects as schema.name, right-click one of its tables or other objects and choose Tools ▸ Hide Schema), and it stays hidden after a restart. To bring them back, right-click the database and choose Show Hidden Schemas, which shows how many are hidden. Hiding only affects the tree, so queries, IntelliSense and scripts still see those schemas. Editing the connection keeps its hidden list, and connections with nothing hidden are saved exactly as before.

Answers [Beekeeper Studio #4791](https://github.com/beekeeper-studio/beekeeper-studio/issues/4791) (sticky schema hiding in the sidebar).

## Competitor issue check

We checked twelve schema-tree and metadata reports from other SQL clients against SQLly. These are ones SQLly already handles or doesn't suffer from:

- [Beekeeper Studio #4718](https://github.com/beekeeper-studio/beekeeper-studio/issues/4718) (table description fetched but never shown) — already have it: Edit Structure… and the table's Properties show and edit the table description.
- [DbGate #1430](https://github.com/dbgate/dbgate/issues/1430) and [DbGate #1210](https://github.com/dbgate/dbgate/issues/1210) (PostgreSQL table and column comments not displayed) — already have it: PostgreSQL table and column comments appear in the structure editor and Properties.
- [DbGate #1217](https://github.com/dbgate/dbgate/issues/1217) (SQL Server table comments shown with the wrong encoding) — checked, SQLly converts SQL Server descriptions to Unicode text before reading them, so non-Latin comments arrive intact.
- [DbGate #1534](https://github.com/dbgate/dbgate/issues/1534) (show user-defined types in PostgreSQL schemas) — already have it: each PostgreSQL schema has a Types folder listing enum, composite and domain types.
- [HeidiSQL #2328](https://github.com/HeidiSQL/HeidiSQL/issues/2328) (show a table's triggers) — already have it: every table has a Triggers folder in the explorer and a Triggers page in Properties.
- [DbGate #1492](https://github.com/dbgate/dbgate/issues/1492) (object pane breaks when switching schemas) — checked, SQLly discards a late answer from an earlier load instead of drawing it over the newer one.
- [DbGate #1221](https://github.com/dbgate/dbgate/issues/1221) (slow with 30,000+ tables because every structure is read up front) — checked, SQLly's explorer lists table names first and loads a table's columns only when you expand it.
- [DBeaver #42370](https://github.com/dbeaver/dbeaver/issues/42370) (a TEMP table named like a SQLite pragma function breaks metadata loading) — checked, SQLly reads metadata on its own connection, and its SQLite metadata queries now name the pragma functions in full, with a test that tries to shadow every one.
