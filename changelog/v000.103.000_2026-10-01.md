# 2026-10-01

## IntelliSense Improvement: a new statement no longer inherits the previous one's context
Typing `update`, `delete`, `insert`, `merge` or `select` after a finished statement — with no `;` between them — now starts a fresh completion context: the popup offers the new statement's tables instead of the previous SELECT's WHERE / JOIN / GROUP BY / ORDER BY keywords, and the old statement's aliases and columns are out of scope (feedback ifb_3798). Every look-back the completion engines make (clause detection, post-FROM and alias positions, in-scope table references, the service-side intent and policy) is now bounded to the caret's own statement, using the same statement splitter the parser and the execution path use, so the boundary rules live in one place. A caret resting right after `UPDATE ` (empty prefix) was also read as the word *before* UPDATE, which left the policy at keywords-only; it now offers the tables, and `INSERT ` leads with `INTO`.

## IntelliSense Improvement: SET offers only what the platform can set
After `SET ` the popup now offers just the connection's settable options — no built-in or user-defined functions and no tables (feedback ifb_0fbc). The engines that spell their settings statement differently steer the caret to their form: on Oracle a plain `SET` leads with an item that rewrites it to `ALTER SESSION SET` (Oracle's `SET` is a SQL*Plus command) and `ALTER SESSION SET ` then offers the session parameters (`NLS_DATE_FORMAT`, `CURRENT_SCHEMA`, `TIME_ZONE`, …); on SQLite `SET` steers to `PRAGMA` and `PRAGMA ` offers the pragmas; and `ALTER SESSION SET` or `PRAGMA` typed on any other platform leads with the item that rewrites it to that platform's `SET`, with a note saying so. `UPDATE … SET` column lists and `SET @var` assignments are untouched.

## IntelliSense Improvement: statement splitter boundaries
The shared splitter now treats `MERGE` as a statement head and start (while leaving `MERGE JOIN` hints and `WHEN MATCHED THEN UPDATE/INSERT/DELETE` actions alone), lets the one-line statements that commonly open an unterminated script (`USE`, `SET`, `DECLARE`, `PRINT`, `EXEC`, `BEGIN TRAN`, …) release the DML that follows them, keeps a `WITH` CTE together with the statement it feeds while splitting the next statement off it, and no longer lets an unclosed parenthesis in a broken statement swallow the UPDATE / DELETE / INSERT / MERGE typed after it. Literals, comments, quoted names, member access, trigger event lists, `FOR UPDATE` and `UPDATE(col)` remain non-boundaries.
