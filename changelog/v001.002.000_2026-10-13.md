# 2026-10-13

## Command-key shortcuts work in the browser on a Mac

In the browser version of SQLLY on a Mac, ⌘A, ⌘Z, ⌘C and the other Command shortcuts did nothing — only the Ctrl versions worked, because the browser build always used the Windows/Linux key layout. On a Mac, ⌘ now acts as the shortcut key everywhere in the browser app (the SQL editor, text fields in dialogs, app shortcuts, and ⌘-click), while Ctrl keeps working too. ⌘V still pastes through the browser so pasting never triggers a clipboard-permission prompt.

## IntelliSense Improvement: typing a number no longer pops up functions

Typing a number in a comparison (`po.PaymentMethodId = 1`) used to open the completion popup on its own with `LOG10` highlighted, because the digit matched inside the function name, so pressing Enter could replace the number with a function. Typing a number now never opens the popup automatically, and asking for completions by hand while on a number offers only value suggestions, never functions, columns or keywords. Asking by hand on an empty value slot still offers functions. `NULL`, `IS NULL` and `IS NOT NULL` are now offered only when the column is known to be nullable, rather than whenever its nullability is unknown (feedback ifb_8765).

## Improve IntelliSense window fits small screens

On a short screen the note box in the Improve IntelliSense window was pushed below the bottom edge. The note box now sits directly under your query, the "What will be sent" explanation is shorter, and the whole right side of the window scrolls.

## Clearer message when the App Store has no price for SQLLY

When the App Store returned no product for the SQLLY unlock purchase, the Unlock dialog said the App Store "couldn't be reached", which was misleading. It now says the price couldn't be loaded and that purchases work in TestFlight and App Store builds once the in-app purchase is available there.

## Re-running a query through a relay no longer comes back empty

Running the same query several times in the browser against a relay sometimes showed the column headers with zero rows, and running it again brought the rows back. For a small result, the rows sometimes arrived before the headers, and the app discarded rows for a result it hadn't seen yet. The engine now always sends the headers, then the rows, then the "query finished" signal, and the app holds back rows that arrive early, so the fix also works against a relay that hasn't been updated yet. This affected the browser app and desktop connections that go through a relay.
